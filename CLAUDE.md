# TyHR: notes for working in this repo

Setup, ports and dev users are in README.md. The build plan and milestones (M0–M8) are in the Tysoft HR plan. M0, M1,
M2, M3 (payroll) and M4 (self-service) are done. M5 (recruitment, hiring, onboarding and probation) is done. M6 (performance: review cycles, goals, appraisals, 360° feedback, calibration, improvement plans and salary reviews) is done. M7 (exits: resignations, notice, clearance, exit interviews, final dues, certificate of service and retention) is done. M8 (reporting, and hardening: load test, tenant-isolation test, backups and the deploy guide in `docs/deploy.md`) is done, so every planned milestone is built.

## Commands

- API: `cd api && dotnet build`, `dotnet test` (Testcontainers: Docker must be running), and `dotnet run --project src/TyHr.Api --launch-profile http`.
- Migrations: `cd api && dotnet ef migrations add <Name> --project src/TyHr.Infrastructure --startup-project src/TyHr.Api -o Persistence/Migrations`. They are applied on startup.
- Web: `cd web && npx tsc -b && npm run lint && npm test && npm run build`. Run all four after web changes.

## Layers (api/src)

- **`TyHr.Domain`:** entities with private setters and invariants in constructors and methods. They throw `DomainException`, which the API returns as a 400 whose message the UI shows, so write messages for an HR user.
- **`TyHr.Application`:** one service per feature plus DTO records. Services take `IAppDbContext`, `ITenantContext`, `ICurrentUser` and `TimeProvider`. Throw `NotFoundException` (in Domain) for 404s.
- **`TyHr.Infrastructure`:** `AppDbContext`, EF configurations, migrations, the Keycloak provisioner, the file store and SMTP.
- **`TyHr.Api`:** thin controllers. Authorization is `[Authorize(Policy = Permissions.X)]`; tenant-scoped endpoints add `[RequireTenant]`.

## Rules that aren't obvious from one file

- **Tenancy:**
  - Every company-owned entity derives from `TenantEntity`. A global query filter limits queries to the request's tenant, and `SaveChanges` stamps and guards the tenant, so never set or filter `Tenant` by hand.
  - The tenant comes from the token's `tenant` claim (MyBiz's shared attribute). Platform admins have none.
  - Background jobs set `ITenantContext.Tenant` themselves, in a scope per company; see `ReminderJob`.
- **Permissions:**
  - Defined once in `Application/Common/Permissions.cs` as permission → roles. `web/src/lib/policies.ts` mirrors it; keep the two in sync.
  - The UI only hides things; the API enforces them.
  - Row-level and field-level visibility of employees lives in `EmployeeAccess`. Line managers see the reporting tree below the employee whose `WorkEmail` matches their sign-in email. Personal and pay sections come back null without permission.
- **Roles:** HR roles are client roles on `tyhr-api`. Realm role `PlatformAdmin` maps to `platform-admin`. Keycloak changes go in `deploy/keycloak/tyhr-clients.json` and `setup.sh`, which must stay safe to re-run, because the realm belongs to MyBiz.
- **Sensitive fields:**
  - Mark with `[Encrypted]`: AES-GCM through an EF value converter, keyed by `Secrets:Key`.
  - Encrypted fields are kept out of the audit trail, and can't be searched or compared in SQL.
- **Audit:** every change to a tenant entity is recorded automatically. Use `[NoAudit]` for bookkeeping tables such as `ReminderLog`.
- **Money:** `decimal`, checked against the company's currency's decimal places (`CountryPack.IsValidAmount`; UGX has 0, KES 2).
- **Country specifics:**
  - `CountryPack` / `CountryFormats` cover ID, tax and phone formats and labels.
  - Add rules there, not as `if (country == "UG")` in services.
  - The UI takes labels from `me.company.country`.
- **Numbers:** `IDocumentNumbers` gives gap-free per-company numbers (EMP-0001) inside the caller's transaction. `IAppDbContext.InTransactionAsync` joins an outer transaction if one is open; the Excel import relies on that to save all rows or none.
- **Files:**
  - Use `IFileStore`: local disk now, S3 later. Storage keys are generated by the system, never taken from file names.
  - Uploads are checked by extension and leading bytes (`FileTypes`), and are always downloaded as attachments.
- **Leave:** the arithmetic is pure domain code (`LeaveCalendar`, `LeaveBalances`; tested in `LeaveRulesTests`). Leave years follow `CompanyProfile.FinancialYearStartMonth`. A request's `Days` is fixed when it's made, so later holiday or working-week edits don't change approved leave. Country leave defaults and holidays live in `CountryCalendar`.
- **Attendance:** punches (`ClockEvent`) are stored in UTC and turned into days by pure domain code (`Timesheet`; tested in `AttendanceRulesTests`) in the company's local time, `CountryPack.UtcOffset` (a fixed +3 for East Africa). Never send a non-UTC `DateTimeOffset` to Npgsql. Schedules apply from `ScheduleAssignment.EffectiveFrom`, else the company default. Corrections are manual punches with a note, never edits. Device exports are parsed by `PunchCsv`.
- **Payroll:**
  - Statutory rules are pure domain code, one class per country (`UgandaPayrollRules`, `KenyaPayrollRules`), with rates in effective-dated tables that say where each came from. A change in the law is a new row, never an edit, so past months still calculate as they did. Golden tests are in `PayrollRulesTests`.
  - `PayCalculator` taxes the month's total pay across all approved and locked runs and deducts only what's still due, so off-cycle and reversal runs come out right.
  - Runs go Draft → Calculated → Submitted → Approved → Locked. Whoever calculated or submitted a run can't approve it. `PayrollRun.Version` (xmin) stops concurrent changes. Locked runs are corrected by reversal, never by editing.
  - Payslips are `[NoAudit]` snapshots, including encrypted payment details.
  - Outputs are in `PayrollOutputService`: QuestPDF payslips (`IPayslipRenderer`, Community licence), emailing after lock (100 a request over one SMTP connection, `IEmailSender.SendManyAsync`; the page repeats while `Remaining` > 0), bank and mobile-money CSVs (formula-safe), and the month's statutory returns from `StatutoryReturns.For(country)` over all approved and locked runs. The journal balances by construction. Employees see their own payslips only from locked runs.
- **Self-service:** employees never edit their own record; they file a `ProfileChangeRequest` (personal, payment or next of kin) that HR approves (payment: payroll or HR admin), never on one's own record. Approval applies only the fields the employee changed. `/api/me/*` covers profile, documents, changes, team and the approvals inbox.
- **Recruitment:**
  - Requisitions (REQ-0001) are approved by an HR admin who didn't raise them; only approved ones are advertised. Managers see only their own.
  - The public careers page (`CareersController`, `/api/public/careers/{slug}`, `[AllowAnonymous]`) sets the tenant from the URL in `CareersService`, for active companies only, and returns only candidate-facing fields. Applying needs consent and a CV (`CvTypes`: PDF or .docx, 5 MB). It's rate-limited per client address and company, and has a honeypot field.
  - The API trusts one hop of `X-Forwarded-For`, because only Caddy can reach it. Don't publish the API's port.
  - In the web app, `/careers/*` renders `CareersApp` from `main.tsx`, without Keycloak or the staff layout.
  - `HiringService` covers interviews, offers and hiring. Interview panels are employees with a work email; they score from `/api/me/interviews` and see the others' scorecards only after sending their own. Interview times arrive in company local time and are stored in UTC.
  - Offer letters are the company's `OfferLetterTemplate` (or the default) with `{{Placeholders}}` filled in, rendered by `IOfferLetterRenderer` (QuestPDF). Emailing an offer is opt-in per send.
  - Hiring needs an accepted offer. It creates the employee through `EmployeeService.CreateAsync` (the salary only if the user may set pay), copies the CV into their documents, and closes the requisition and its postings once all openings are filled.
- **Onboarding and probation:**
  - `OnboardingTemplate`s are checklists; starting onboarding (from the employee, or on hire) copies one, or the default, or `OnboardingTemplate.Standard`, into `OnboardingTask`s due relative to the hire date. Manager tasks go to the line manager, IT tasks to an IT contact, new-hire tasks to the employee, and HR's (or unassigned) to HR. Owners tick theirs off from `/api/me/tasks`; HR (`EmployeesManage`) can tick off any.
  - `ProbationService`: unconfirmed probations ending within 30 days or ended within the last 90 are due. The line manager (anyone above them in the reporting tree) recommends and HR decides, never on their own record; deciding confirms or extends the `EmploymentContract`. The daily reminder job also emails line managers about their reports' probations.
- **Performance:**
  - `ReviewCycle` goes Draft → GoalSetting (launch makes an `Appraisal` per current employee in scope, hired by the period end) → Review → Closed. It keeps its own five-label rating scale.
  - An appraisal's reviewer is the line manager at launch (`Appraisal.ManagerId`, which HR can change); without one, HR (`PerformanceManage`) reviews. Nobody reviews themselves. `PerformanceService` works out the user's role per appraisal and hides other people's appraisals as not found.
  - Goals carry weights that must total 100 before they're sent or agreed. Self ratings show to the reviewer only once sent, and the manager's to the employee only once complete. The overall rating is the weighted average of the manager's ratings.
  - `FinalRating` is the rating that counts (distribution, results, salary review). It equals `OverallRating` unless the cycle has `Calibrate`: then finished manager reviews wait in `Calibration`, HR may change the final rating (with a reason, never their own), and `ReleaseResults` completes them and emails employees. Later reviews go straight to Completed.
  - 360° feedback (`PeerFeedback`, cycle option): the reviewer or HR asks colleagues with a work email during the review; they answer from `/api/me/feedback`. Only the reviewer and HR see it, never the employee.
  - `ImprovementPlanService`: HR, or a line manager for their reporting tree, runs plans (objectives, check-ins, outcome); the employee reads and acknowledges their own; nobody manages their own. One active plan per employee.
  - `SalaryReviewService` (`EmployeesPay` only): a per-cycle guideline (% per rounded final rating, effective date) makes recommendations from the salary in force before that date. Hand adjustments survive guideline changes. Applying records `SalaryChange`s through `EmployeeService.AddSalaryAsync`, all or none.
- **Exits:**
  - `ExitService`: an employee resigns from `/api/me/resignation` (Requested) and HR (`ExitsManage`) accepts it, or HR records an exit directly (InProgress). Only one open exit per employee (filtered unique index). Nobody handles their own.
  - Statutory notice comes from `CountryPack.Exits` (`ExitRules`: Uganda s.58 by service, Kenya 28 days). It's advice: short notice without pay in lieu is a warning, not an error.
  - Accepting or recording an exit copies `ClearanceStep.Standard` into `ClearanceItem`s due relative to the last working day. Owners clear theirs from `/api/me/clearance` (shown in My tasks); finance items go to payroll (`PayrollPrepare`); HR can clear any. The leaver never clears others' items on their own exit.
  - The exit interview is HR's only. Once the leaver fills it in, HR can't change it.
  - Completing needs the last working day to have passed and clearance done. It sets `EmployeeStatus.Exited` (the only way to), ends contracts (`EmploymentContract.EndOn`) and cancels leave starting later. Exited people can't use self-service.
  - The regular payroll pays leavers (exit InProgress or Completed) up to their last working day, and skips those whose last day was before the month.
  - `FinalDuesService` (`EmployeesPay`; sending needs `PayrollPrepare`): `FinalDues.Suggest` (pure) works out unused ANNUAL leave at a working-day rate (basic × 12 ÷ 52 ÷ working days a week), notice in lieu (basic ÷ 30 a day) and severance from `ExitRules.Severance`. It uses the LEAVEPAY, NOTICEPAY, SEVERANCE and LEAVEREC components, created on first use, so tax treatment follows their settings. Saved lines go to an off-cycle run for the last day's month; deleting that run while it's a draft puts the dues back to draft.
  - `CertificateService` renders the certificate of service (`ICertificateRenderer`, QuestPDF) for completed exits: facts only, never the reason or a view of their work.
  - Retention: `CompanyProfile.RetentionYears` (5–25, default 7) after the last working day. `ArchiveService.AnonymiseAsync` (`RecordsRetention`, HR admin) then removes personal data from the employee and their payslips, deletes next of kin, documents (and files), change requests and the exit interview, and redacts their audit entries' values. Employment and pay history stay under the employee number. It can't be undone and never runs automatically.
- **Reports:** `ReportsService` (`ReportsView`: HR and payroll) works out headcount, turnover (12 months to today; voluntary = resignation or retirement; rate = leavers ÷ average month-end headcount), leave liability (ANNUAL available today, valued at the final-dues daily rate only with `EmployeesPay`) and payroll cost (approved and locked runs, from payslips, only with `PayrollView`), in memory. Leaving reasons need `ExitsManage`. `ExportAsync` writes one sheet per report the user may see. The web page is `/reports`, with small single-hue charts in `features/reports/charts.tsx`.
- **Dates:** `DateOnly` for calendar dates; the web sends and receives `YYYY-MM-DD` strings. Use `TimeProvider` (`clock.GetUtcNow()`), never `DateTime.Now`. Tests use `TestClock`.

## Tests (api/tests/TyHr.Tests)

- Integration tests run against real Postgres with the real migrations (`PostgresFixture`). Each test makes its own company with `fx.CreateTenantAsync()`, so tests don't share data.
- `fx.NewScope(tenant, roles:, email:)` acts as one request. Services are built by hand in the test class: see `Hr` in `CoreHrTests.cs` and `As(...)` in the others.
- `TenantIsolationTests` calls every endpoint as another company with all of a company's record ids. A new table must be `ITenantOwned` (or listed there as shared), and a new controller needs `[RequireTenant]`. New tables are covered automatically: `FillRemainingTablesAsync` makes a marked row in each one `FillAsync` leaves empty.
- Opt-in: `TYHR_LOAD=5000 dotnet test --filter LoadTests` (payroll at scale), and `TYHR_SMTP=localhost:1025 dotnet test --filter SmtpTests` (needs Mailpit).
- Write test names as sentences about behaviour, and assert user-facing messages with `Contains`.

## Web (web/src)

- `features/<area>/` holds pages and their forms. `api/types.ts` mirrors the DTOs, and `api/client.ts` adds problem-details messages, uploads and authenticated downloads.
- Use `useApiMutation` (toasts, plus invalidating query keys by their first segment), `useCan('policy')` and the `PageHeader`/`Loading`/`LoadError` components.
- Routes are lazy: add a page in `router.tsx` with `page(() => import(...), 'Name')`, and in `AppLayout`'s nav with its policy.
- The menu (`components/Sidebar.tsx`, `layout.css`) follows Tycount's (`erp/my-biz/src/navigations`): everyday links, then one collapsible section per area, an icon rail when collapsed, and a drawer on phones. Keep its colours in the `--frame-*` variables. `lib/activeLink.ts` picks the one link to highlight.
- Mantine `DateInput` values are `YYYY-MM-DD` strings. Turn empty strings into `null` before sending (`orNull`).

## Production

- `docs/deploy.md` is the deploy guide; keep it in step with `docker-compose.prod.yml`, `deploy/` and new settings.
- TyHR shares MyBiz's (Tycount's) server and borrows its Caddy, Keycloak and Postgres over the `tyhr-edge` network (`deploy/tycount.override.yml`, the website's pattern). Never edit MyBiz's repository for this.
- Compose service names start with `tyhr-`, because Tycount's Caddy is on this network too and a service called `api` would take some of Tycount's traffic.
- The API talks to Keycloak at `http://keycloak:8080`: Tycount's Caddy blocks `/admin` from outside, which invitations need.
- `/etc/caddy/sites` can only be mounted once, so `deploy/caddy/sites/tysoft-website.caddy` re-imports the website's files. TyHR's override goes last in Tycount's `COMPOSE_FILE`.
- Everyone signs in at `https://TYHR_DOMAIN`. `setup.sh` registers it on `tyhr-web` and keeps addresses already there.
- `create-db.sh`, `backup.sh` and `restore.sh` touch only the `tyhr` database in the shared Postgres. They were tested on a simulated shared server; repeat that after changing them.

## Local database

- Development uses the shared Tysoft Postgres (`postgres_container`, localhost:5432), database and role `tyhr`, set up by `deploy/postgres/setup-dev.sh`. The connection string is in user-secrets, not appsettings. Other products' databases are on that server: touch only `tyhr`.
- Tests still use their own Testcontainers Postgres.

## Don'ts

- Don't edit the MyBiz realm by hand or change anything of MyBiz's. Go through `setup.sh` and TyHR's own clients.
- Don't commit `*.local.txt`, `.env.prod` or `data/`.
- Don't add Keycloak or a second auth realm to the compose files. Sign-in is MyBiz's Keycloak.
